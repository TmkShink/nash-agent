# 面试追问手册

这份手册随实现更新。回答时先说系统当前怎么做，再解释取舍和失效条件；没有实现的能力要直接说明。

## 为什么采用自由循环

**问：为什么没有先让模型生成完整计划，再严格按计划执行？**

真实编程任务的观察结果会改变后续步骤。测试报错、搜索结果和代码结构都可能推翻原计划。Nash 让模型在每次 observation 后重新决定下一步，runtime 只控制权限、预算和终止。固定工作流更容易预测，但会把错误假设固化到后续节点。

**追问：自由循环会不会让模型漫无目的地调用工具？**

会，所以 runtime 维护最大 turn、最大工具调用数和重复失败计数。轨迹还会记录每次工具调用，便于区分模型能力问题、提示词问题和工具反馈问题。仅靠 system prompt 要求“不要绕圈”没有硬保证。

## 工具为什么这样设计

**问：为什么文件修改用精确替换，而不直接让模型重写整份文件？**

精确替换会检查旧文本是否存在且只出现一次。代码已经变化或匹配不唯一时，工具拒绝写入，模型需要重新读取文件。这样能减少基于过期上下文覆盖用户修改的概率。完整写入仍适合创建新文件，但覆盖已有文件需要更明确的意图。

**追问：为什么不用统一的 shell 工具完成所有文件操作？**

专用文件工具能在执行前做路径检查，也能返回稳定的结构化错误。全部交给 shell 会缩短实现，却把路径越界、输出截断和错误分类都变成提示词约定，runtime 很难审计。

## 安全边界能保证什么

**问：给 shell 命令加黑名单能否避免危险操作？**

不能。shell 允许重定向、子进程、脚本解释器和编码后的命令，字符串规则很容易绕过。Nash 把人工审批或外部沙箱作为安全边界，命令过滤只能辅助提示风险。`--yes` 适合受控演示目录，不应被描述为安全模式。

**追问：工作区路径检查是否会被符号链接绕过？**

只检查字符串前缀会被 `..` 和符号链接绕过。实现需要同时规范化路径，并检查已存在路径的真实位置。创建新文件时还要验证最近的已存在父目录。这里仍有 TOCTOU 风险；面对不可信并发进程时，应把 Agent 放进操作系统级沙箱。

## 轨迹与恢复

**问：JSONL 轨迹能不能做到确定性 replay？**

它能确定性重放已经记录的界面和状态转换，不能保证重新执行工具得到相同结果。文件系统、时间、网络和外部命令都可能变化。若要做执行级 replay，需要保存工作区快照、环境信息和工具结果，并明确哪些副作用只读取记录而不再次执行。

**追问：进程在写文件后、记录 tool result 前崩溃怎么办？**

这暴露了文件系统副作用与事件日志之间无法原子提交的问题。首版通过在执行前记录 tool started、执行后记录 tool finished 来识别悬空调用，但不能自动判断副作用是否发生。恢复时应停止并请求人工确认，不能盲目重试非幂等操作。

## 如何判断是模型问题还是 harness 问题

固定模型、提示词、初始仓库和预算，重复运行一组带确定性验证器的任务，再比较成功率、调用数、耗时和失败分类。模型从未提出正确行动偏向模型或上下文问题；正确调用被工具拒绝、结果被截断到无法使用或状态写回错误，则偏向 harness。单次演示不能证明普遍能力，所以仓库需要保留可复现的 smoke task。

## 后续需要补充的高压问题

- 并行 tool call 如何保持结果顺序，又如何处理部分成功？
- context compaction 如何验证没有改变用户约束？
- 模型输出的 tool arguments 通过 JSON Schema 后，为什么仍然不可信？
- token 预算、金额预算和 wall-clock deadline 发生冲突时谁优先？
- provider 在流式响应中断线，怎样避免重复执行已经收到的 tool call？
- 如何防止工具输出中的 prompt injection 改写系统目标？
- 怎样设计评测，避免只针对演示任务过拟合？
